# Proposed Pulse integration — not implemented, awaiting separate approval

Inspected Pulse's existing internal/gateway/server.go: it authenticates its console/history routes and upgrades /api/stream to a long-lived WebSocket. Worker requests have a separate bearer token. The current Throttle HTTP proxy strips the caller's Authorization and has bounded request deadlines. Putting it blindly in front of Pulse would break its identity/stream lifetime and would count handshakes rather than costly voice turns. No Pulse files or dependencies were changed.

A small separate integration should first expose a narrow public Go admission package from Throttle (the current internal package is deliberately not importable from another repository). Then Pulse can call that package after its existing authentication and before accepting a new expensive turn, using an explicitly configured service/client label. Do not derive identity from a forwarded header or invent multi-user tenancy from Pulse's single-operator demo. Keep Pulse's worker token private and preserve its existing cancellation/generation fencing.

Start with fixed token-bucket admission for a reviewed voice-turn route, leaving all streaming sockets and backend timeouts owned by Pulse. Review endpoint classification and response/error semantics before enabling adaptation; the current synthetic endpoint catalog is not a voice API catalog. Do not train client blame from worker/server failures. Return a structured existing-protocol rejection without dispatching work; do not retry a voice turn automatically.

The reviewable change would include unauthorized-access regression tests, a repeated-turn abuse fixture, cancellation/barge-in and stream-lifetime regression tests, and measured added turn-admission overhead using the same real CPU model baseline. Re-run both projects' independent gates and report successful-turn/latency tradeoffs. Deployment remains a separate approval. No claim of completed integration is made here.
